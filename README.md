# Тестовый модуль учёта платежей

Full-stack приложение для демонстрации учёта платежей по заказам. В проекте есть 12 тестовых заказов, приём частичных и полных оплат, разрешённая переплата, история операций, идемпотентность, защита от конкурентных запросов и сводный отчёт.

## Что реализовано

- NestJS API на TypeScript с разделением `Controller → Service → Repository`.
- React/Vite интерфейс на русском языке: реестр заказов, карточка заказа, добавление платежа, история и отчёт.
- PostgreSQL 16 как источник истины; денежные суммы хранятся в целых копейках (`bigint`).
- Redis 7 как быстрый дополнительный кеш соответствия `idempotencyKey → paymentId`.
- TypeORM-миграция создаёт схему, ограничения и идемпотентно добавляет 12 заказов.
- Docker Compose с healthcheck для всех четырёх основных сервисов.
- Jest unit-тесты и интеграционные тесты на реальных PostgreSQL и Redis, включая конкурентные запросы.
- Единый формат ошибок: `{ "error": { "statusCode", "message", "path", "timestamp" } }`.

## Архитектура

```text
backend/src/
  orders/       # controller, service, repository, entity
  payments/     # controller, service, repository, DTO, entity
  reports/      # агрегированный отчёт
  health/       # проверка приложения, PostgreSQL и Redis
  database/     # DataSource, миграция и запуск миграций
  redis/        # дополнительный быстрый слой идемпотентности
frontend/src/
  pages/        # реестр, карточка заказа, отчёт
  components/   # таблица, суммы, статусы, состояния
```

Модульный монолит выбран потому, что предметная область небольшая, а для тестового проекта важны простой запуск и одна транзакционная граница. Модули изолируют обязанности и позволяют позже вынести части системы, но не добавляют сетевую сложность микросервисов.

## ACID, конкурентность и идемпотентность

Добавление платежа выполняется в одной транзакции PostgreSQL:

1. строка заказа блокируется `SELECT ... FOR UPDATE`;
2. платёж ищется по `idempotencyKey`;
3. при отсутствии дубля создаётся запись;
4. внутри той же транзакции суммируются платежи и обновляется статус;
5. изменения фиксируются атомарно.

Уникальное ограничение `uq_payments_idempotency_key` остаётся последней линией защиты на уровне БД. Блокировка заказа сериализует параллельные платежи одного заказа, поэтому суммы не теряются. Redis ускоряет повторный запрос, но найденный там ID всегда перепроверяется в PostgreSQL; при недоступном Redis операция продолжает работать через БД.

## Запуск

Требуются Docker и Docker Compose:

```bash
docker compose up --build
```

После готовности сервисов:

- frontend: http://localhost:8080
- API: http://localhost:3000/api
- health: http://localhost:3000/api/health

Миграция запускается backend-контейнером перед приложением. Повторный запуск безопасен: TypeORM не повторяет применённую миграцию, а seed использует фиксированные UUID и `ON CONFLICT DO NOTHING`.

Остановка: `docker compose down`. Команда `docker compose down -v` дополнительно удалит локальный volume и все демонстрационные данные.

## Тесты и сборка

Unit- и интеграционные тесты в контейнере с реальными PostgreSQL/Redis:

```bash
docker compose --profile test run --rm backend-test
```

Локально, если PostgreSQL и Redis доступны на `localhost` с параметрами из `.env.example`:

```bash
npm install
npm run migration:run -w backend
npm test
npm run test:integration
npm run build
```

## Примеры API

```bash
curl http://localhost:3000/api/orders
curl http://localhost:3000/api/orders/10000000-0000-4000-8000-000000000001
curl http://localhost:3000/api/reports/summary
curl http://localhost:3000/api/health
```

Добавление платежа:

```bash
curl -X POST http://localhost:3000/api/orders/10000000-0000-4000-8000-000000000001/payments \
  -H "Content-Type: application/json" \
  -d '{"amount":"500.00","idempotencyKey":"demo-payment-001"}'
```

Первый ответ имеет HTTP 201 и `created: true`; повтор — HTTP 200, `created: false`, `duplicate: true`.

## Компромиссы тестового проекта

- Статус заказа хранится для быстрого чтения, хотя его можно восстановить из платежей; обновление защищено той же транзакцией.
- Redis-кеш имеет TTL 24 часа и не содержит критичных данных.
- Seed включён в начальную миграцию ради предсказуемого однокомандного запуска.
- Интерфейс не содержит сортировку и пагинацию: для 12 записей они не нужны.

При production-развитии потребовались бы аутентификация и роли, неизменяемый аудит, outbox для интеграционных событий, observability, rate limiting, retry/DLQ, метрики и трассировка, полноценный CI/CD, резервное копирование, ротация секретов и security review. Эти функции в текущем проекте не реализованы.
